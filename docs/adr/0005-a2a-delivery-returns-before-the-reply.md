# A2A deliveries return before the reply

A2A is the lifecycle of a delivery from one Node to a neighboring Node along a Link. The participants stay Nodes. A Binding is still the session on this machine, and that session runs one pi agent loop. Clowder can leave a successful answer in a shared timeline. Here each Node has its own session, so the answer has to be brought back on purpose.

`send_flow_message` returns the delivery's state at that moment: still a Queue Entry, already a Chat History Message, or already failed. It does not stay open until the target Node writes a reply. A Queue Entry has not appeared in the target transcript. While that session is replying, the text waits outside it. Deliveries to the same Node enter the transcript in the order they were created, one at a time. They survive a process restart. A failed one is not sent again.

The target Node starts the Active Run for that delivery. Flow records Read then, and does not tell the sender. If that run ends with no Reply, Flow reminds the target once, citing the delivery id. A Reply is the one answer submitted for that id. It is written into the sender's session as a user message, not as another A2A delivery. The sender's loop is started again if it has ended, or given the message as a follow-up if it is still running. A second Reply for the same id is refused. If the run ends with no assistant text and no Reply, the sender is told the delivery failed, not handed an empty answer. A failure discovered only after the tool returned wakes the sender the same way, as many times as it happens. The model decides whether to send a new delivery.

The Link stays lit from the send until the Reply or the failure. Lighting it only until the text enters the transcript would look like the exchange was finished while the sender still had no answer.

Considered waiting inside the tool until the target finished, and considered a Chain id that counted hops across Nodes, including an eight-hop cap and a hidden comment in the transcript. A wait deadlocks when the downstream run never ends or when the wait forms a cycle. A Chain cannot tell that B messaged C because of A. Also considered copying Clowder's rule that success does not call the sender back. That fits one shared transcript, not two sessions. Considered treating the target's last assistant text as the Reply, and letting the sender poll for Read. The Reply is explicit, and Read stays on the delivery because the sender's loop may already have ended.
