# 会话状态投影 Dogfood 记录

## 目标

这次 dogfood 使用 piflow 自己推进“服务端权威的会话状态投影”。目标不是增加一套 Agent runtime，而是让 Flow 画布在用户没有打开具体会话时，仍能可靠显示由 pi runtime 产生的 `idle`、`running` 和 `failed` 状态。

实现保持了三层边界：

- pi 是唯一的 Agent runtime，负责会话、模型调用、工具执行和生命周期事件。
- piflow server 订阅 pi 的结构化事件，维护当前进程内的状态事实。
- Web 通过 SSE 接收全量快照和增量事件，只负责渲染投影，不再根据浏览器是否打开过会话推断节点状态。

## 实际过程

本次工作拆成两个相连的 Flow 节点：Runtime 节点负责 protocol 和 server，Canvas 节点负责 Web 消费。Runtime 通过 `send_flow_message` 把明确的前端任务交给 Canvas；Canvas 完成后回传结果，Runtime 再执行集成检查。

这个过程验证了对等节点可以按模块并行保存各自上下文，并通过显式消息传递交付有限信息。它也暴露出：仅有消息路由和节点运行灯，还不足以帮助用户持续判断多个长会话是否值得继续复用。

## 本次真实验收

重启 3141 后，浏览器重新进入 Flow 画布，未打开具体聊天会话。通过 server API 后台打开 Flow Activity 节点并发送只读验收任务，Kimi K2.7 两次都在 provider 侧因当前额度/请求状态立即结束，未能形成可观察的长 `running` 窗口。服务端 SSE snapshot 正确记录该节点为 `failed`；刷新浏览器后画布仍显示“需要处理”，没有回退为默认的“空闲”。

因此本次真实环境确认了 `failed` 的服务端投影与刷新恢复；`running` 的生命周期由 agent 事件处理、SSE 快照测试和类型/构建检查覆盖，但由于 provider 在运行前失败，未声称完成真实长任务的视觉验收。

## 本次实现

服务端为已加载的会话维护内存状态表：

- 创建或打开会话时记录 `idle`。
- 收到 `agent_start` 时记录 `running`。
- 收到 `agent_settled` 时检查最近一条 assistant 消息；`stopReason` 为 `error` 时记录 `failed`，否则记录 `idle`。
- prompt 或异步 Flow 消息派发失败时记录 `failed`。
- 状态变化通过 `status_delta` 广播。
- SSE 建立或重连时，在 `hello` 后发送 `status_snapshot`。

Web 以 `sessionFile` 为持久会话的状态键，并用 `updatedAt` 拒绝旧增量覆盖新状态。同一时间戳下，后到达的 SSE 消息获胜，因为单条 SSE 连接本身保证消息顺序。Flow 节点直接读取该状态表，不再依赖聊天视图是否曾被浏览器创建。

集成审查还发现，`send_flow_message` 的目标会话启动失败时，旧回调会把错误归到发送方。状态投影加入后，这会进一步把错误节点标成 `failed`。本次将派发失败回调改为携带目标会话，并按目标 `sessionPath` 发布错误和状态。

## 观察到的问题

### 1. 旧会话继续了错误目标

Canvas 节点曾重新进入旧任务，而不是执行最新委托。直接原因是 dogfood 时复用了一个包含未完成旧任务和两次 timeout 的长会话。piflow 忠实保留并继续使用了这段上下文；这不是 piflow 自动制造的上下文腐化，而是使用者选择了不合适的会话。

当前设计会放大这个错误：节点只展示名称、静态目标和粗粒度运行状态，不展示上一次任务是否完成、最后结果、未完成队列或上下文压力。模块型节点因此很容易被误解为可以无限复用的“长期角色”，用户难以判断它究竟仍在延续旧任务，还是已经适合接受一个新目标。

改进方向：优先增加可判断的信息，而不是自动清空或总结上下文。节点应逐步展示最近任务结果、待处理状态和上下文用量，并在跨节点派发时让用户或发起 Agent 明确选择“继续当前会话”还是“创建干净会话”。新会话不应自动继承完整历史，只接收本次任务需要的目标、约束和证据引用。

### 2. 开发服务器重启中断了 Agent

修改 shared protocol 时，`pnpm dev` 的 server watch 会重启整个 piflow server。Agent session 运行在这个进程内，因此正在执行的模型请求和工具调用会被直接终止。这是当前开发部署方式导致的明确机制问题，不是模型上下文腐化。

浏览器此前仍可能显示“回复中”，因为运行状态来自本地聊天视图；server 重启后没有权威快照纠正它。此次状态投影解决了浏览器刷新、SSE 重连和遗漏历史事件后的状态重建，但内存 registry 会随 server 一起消失，因此无法把已经丢失的 Agent 恢复为运行中。

改进方向：开发阶段先避免在 dogfood 任务运行时触发 server watch 重启，并在连接世代变化后将上一世代的 `running` 显示为 `interrupted`，而不是 `idle` 或永久 `running`。真正的进程重启恢复需要持久化执行记录和 pi runtime 的恢复能力，在基础状态语义稳定前不应伪造自动续跑。

### 3. 停止和排队缺少可见反馈

abort 请求可能需要等待当前 provider 或工具响应，界面却没有“正在停止”状态。向忙碌节点发送消息时，实际行为是进入 follow-up 队列，但现有文案容易让人误以为消息会立刻改变当前执行。

当前三态模型只回答“是否运行或失败”，不能表达用户是否应该等待、干预或检查结果。它也没有显示当前子目标、最近一次有效动作和工具已运行时间，长调用会表现为一个没有解释的运行灯。

改进方向：在验证三态投影可靠后，再从 pi 的结构化事件派生 `stopping`、`needs_input` 和 `review_ready` 等注意力状态；队列应明确区分当前 turn、steering 和 follow-up，并显示消息会在何时生效。不要通过解析自然语言猜测这些状态。

### 4. 测试挂起无法定位

SSE 测试早期因为 heartbeat 定时器未关闭而挂起。Flow 画布只能看到节点持续运行，无法判断它停在测试、工具还是模型请求，也看不到持续时间。

改进方向：节点保持简洁，但应能展开最近活动摘要，包括当前工具、开始时间和最后事件。详细日志仍属于会话视图或后续 Trajectory，不应把完整终端输出复制到画布。

## 根因分类

| 类别 | 本次实例 | 判断 |
| --- | --- | --- |
| 操作失误 | 复用带有未完成旧任务的长会话 | piflow 没有制造腐化，但缺少信息帮助用户避免误用 |
| 设计放大因素 | 节点缺少最近结果、未完成状态和上下文压力 | piflow 让错误选择更容易发生且更难被及时发现 |
| 机制缺陷 | server watch 中断 Agent、重启后状态失真、abort 和队列反馈不足 | 应由 piflow 的 runtime 投影和交互语义直接修复 |
| 本次已修复 | 未打开会话时的状态依赖浏览器本地 view | 改为 server snapshot/delta，刷新与重连可重建状态 |

## 正确的演进顺序

1. 先验证 `idle`、`running`、`failed` 在后台执行、刷新、重连和错误场景下始终正确。
2. 增加 `interrupted`，区分“当前空闲”和“上一个 server 世代中的执行已丢失”。
3. 增加用户注意力投影，优先表达 `needs_input`、`review_ready` 和 `stopping`。
4. 为节点提供最近任务结果、当前动作、排队消息和上下文压力的紧凑摘要。
5. 改进跨节点派发入口，明确继续旧会话与创建干净会话的差异。
6. 最后再设计可恢复的 Flow 活动账本和 Trajectory，记录消息传递与证据访问的来源，但不复制完整 pi transcript。

## 暂不处理

- 不把 Flow 状态表扩展为通用 registry 或插件框架。
- 不让浏览器成为执行状态的事实来源。
- 不持久化或复制完整模型上下文。
- 不把对等 Flow 节点改成父子 Agent。
- 不声称 server 重启后可以恢复已被终止的 Agent。
- 不把外部 TUI 或独立 pi 进程的状态纳入当前内存 registry。

## 验收标准

- 后台启动一个从未在浏览器打开的 Flow 会话，节点显示 `running`。
- 运行期间刷新页面或重连 SSE，节点通过 snapshot 恢复为 `running`。
- 正常完成后节点变为 `idle`。
- assistant 以 `stopReason: error` 结束或 prompt 抛错后，节点保持 `failed`。
- 旧状态增量不能覆盖更新的状态。
- server 重启后的限制在产品和技术文档中被明确描述，不伪装成执行恢复。
